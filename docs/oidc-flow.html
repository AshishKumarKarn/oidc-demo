2 · Architecture

Solid arrows are direct HTTP calls; the dashed arrow is the resource server fetching the provider's public keys (JWKS) to verify tokens offline — it never sees the user's credentials.

3 · Sequence of the full flow

Dashed blue arrows are responses. The PKCE code_verifier stays inside the client until the back-channel token call (step 5), so an intercepted authorization code is useless without it.

3Authorization request — redirect the user to sign in

The client generates a PKCE pair and redirects the browser to /authorize. The code_challenge is BASE64URL(SHA256(code_verifier)); the verifier never leaves the client until step 5.

code_verifier  B2TogbJV6k3a2HuMZdyfP3yCcaeI-fMLJihvPv7T734
code_challenge YYqRk8QFFnUBuVzn2nRNZjywAleTbd8sDJ9ttf_h5K8
state        d5ddfec58c45babc
nonce        b2e72d4bdb24d15e

Request
curl -s -G http://localhost:9000/authorize \
  --data-urlencode 'response_type=code' \
  --data-urlencode 'client_id=demo-client' \
  --data-urlencode 'redirect_uri=http://localhost:8080/callback' \
  --data-urlencode 'scope=openid profile email api.read' \
  --data-urlencode 'state=d5ddfec58c45babc' \
  --data-urlencode 'nonce=b2e72d4bdb24d15e' \
  --data-urlencode 'code_challenge=YYqRk8QFFnUBuVzn2nRNZjywAleTbd8sDJ9ttf_h5K8' \

4Login — user authenticates, provider issues a code

The user submits credentials. The provider validates them, mints a single-use authorization code (TTL 60s) bound to the client, redirect URI, scope, nonce and PKCE challenge, then 302-redirects back to the client. The state is returned unchanged so the client can detect CSRF.

Request
curl -s -i http://localhost:9000/login \
  -d 'username=alice' -d 'password=password' \
  -d 'client_id=demo-client' \
  -d 'redirect_uri=http://localhost:8080/callback' \
  -d 'scope=openid profile email api.read' \
  -d 'state=d5ddfec58c45babc' -d 'nonce=b2e72d4bdb24d15e' \
  -d 'code_challenge=YYqRk8QFFnUBuVzn2nRNZjywAleTbd8sDJ9ttf_h5K8' \
  -d 'code_challenge_method=S256'
Response
HTTP/1.1 302
Location: http://localhost:8080/callback?code=a2fa6a0c340b49328e513e47a78ec06f&state=d5ddfec58c45babc

5Token exchange — swap code (+verifier) for tokens

The client calls the back-channel /token endpoint, authenticating with HTTP Basic (client_secret_basic) and presenting the original code_verifier. The provider re-derives the challenge from the verifier, confirms it matches what was stored in step 4, and only then returns an access token and an ID token (both RS256 JWTs).

Request
curl -s -X POST http://localhost:9000/token \
  -u 'demo-client:demo-secret' \
  -d 'grant_type=authorization_code' \
  -d 'code=a2fa6a0c340b49328e513e47a78ec06f' \
  -d 'redirect_uri=http://localhost:8080/callback' \
  -d 'code_verifier=B2TogbJV6k3a2HuMZdyfP3yCcaeI-fMLJihvPv7T734'
Response
{
  "access_token": "eyJraWQiOiIzMDUyOTdjMi0z\u20265kYwW1_78hjQ",
  "scope": "openid profile email api.read",
  "token_type": "Bearer",
  "id_token": "eyJraWQiOiIzMDUyOTdjMi0z\u2026qIt_gxtrpZ4Q",
  "expires_in": 300
}

5aAnatomy of the tokens (decoded)

Both JWTs are signed with RS256. Decoding the Base64URL segments shows why each token exists: the ID token’s audience is the client (it proves who the user is, and echoes the nonce), while the access token’s audience is the resource server (it grants what the bearer may do, via scope).

Access token (header + claims)

  "kid": "305297c2-3c43-4f73-8495-ed75d365a4ea",
  "typ": "JWT",
  "alg": "RS256"
}

6UserInfo — fetch claims with the access token

Optionally, the client calls the provider's /userinfo endpoint with the access token. The returned claims are filtered by the granted scopes: profile adds name/username, email adds the email claims.

  -H "Authorization: Bearer $ACCESS_TOKEN"
Response

  "sub": "user-001",

  "name": "Alice Anderson",
  "preferred_username": "alice",
  "email": "alice@example.com"

8Protected API — call /api/me with the Bearer token

Now the client calls the protected API. The resource server's servlet filter extracts the Bearer token, verifies its RS256 signature against the cached JWKS, and enforces the expected iss, aud (resource-server) and exp. The validated claims drive the response.

Request
curl -s http://localhost:9100/api/me \
  -H "Authorization: Bearer $ACCESS_TOKEN"
Response
{
  "scopes": [
    "profile",
    "openid",
    "email",
    "api.read"
  ],
  "subject": "user-001",
  "clientId": "demo-client"
}

5 · Error responses

The same endpoints, exercised with a missing or under-privileged token. These show how the resource server distinguishes authentication (401) from authorization (403).

E1401 Unauthorized — no Bearer token

Calling a protected route without a token. Per RFC 6750 the server replies with a WWW-Authenticate: Bearer challenge header.

Request
curl -s -i http://localhost:9100/api/me
Response
HTTP/1.1 401
WWW-Authenticate: Bearer error="missing_token",
  error_description="A Bearer access token is required"

{
  "error": "missing_token",
  "error_description": "A Bearer access token is required"
}

E2403 Forbidden — token valid but scope insufficient

Here a second user (bob) logged in requesting only openid profile — no api.read. The token is perfectly valid and /api/me would succeed, but /api/messages rejects it with insufficient_scope.

Request
# token obtained with scope='openid profile' (no api.read)
curl -s -i http://localhost:9100/api/messages \
  -H "Authorization: Bearer $NARROW_TOKEN"
Response
HTTP/1.1 403

{
  "error_description": "This endpoint requires the 'api.read' scope",
  "required_scope": "api.read",
  "error": "insufficient_scope"
}

6 · Why each check matters

  • PKCE (S256) — binds the authorization code to the client instance that started the flow. A stolen code cannot be redeemed without the matching code_verifier.
  • state — returned unchanged on the /callback redirect so the client can reject cross-site request forgery.
  • nonce — embedded in the ID token and checked by the client to prevent token replay.
  • Single-use code, 60s TTL — the code is consumed atomically at the token endpoint, so replay fails even within the window.
  • aud separation — the ID token is for the client, the access token is for the API; neither is accepted in the other's place.
  • Signature + iss/aud/exp on every API call — the resource server trusts no token it cannot verify against the provider's JWKS, with no shared secret and no call back to the OP per request.
Demo only. Secrets are hard-coded, users and keys live in memory, transport is plain HTTP, and there is no refresh-token or consent handling. The point is to make every protocol step visible.
